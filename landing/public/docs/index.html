Hatch documentation

Hatch runs temporary previews for GitHub pull requests on your infrastructure. A preview can include your app, database, cache and workers. Hatch posts the preview link on the PR.

Deploy Hatch

  • Docker Compose runs Hatch behind Traefik with previews on the Docker host.
  • Kubernetes and Argo CD use a remote BuildKit builder, a container registry and preconfigured preview namespaces.

Quickstart

  1. Install and configure a GitHub App for your Hatch instance. Subscribe to pull_request and issue_comment, and install the app on a repository whose owner is allowed by Hatch.
  2. Add a Dockerfile and this .hatch.yml at the repository root. Set port to your app's listening port.
version: 1
services:
  web:
    build: .
    port: 3000
    expose: true
  1. Open a pull request and leave the comment @hatchpr preview by itself. Use your instance's bot handle if it differs.
  2. Wait for Hatch to post the preview link. Comment again after pushing a commit to update the preview. Closing the PR removes the preview.

When to add .hatch.yml

A root Dockerfile is enough for a single web service. Use .hatch.yml to set an explicit port, add services, seed a database or change when builds run.

Generate a configuration with the CLI

Run this at the root of your repository to preview the generated configuration:

npx @hatchpr/cli init --dry-run

Run npx @hatchpr/cli init to write the file. Use --output to choose a path, --verbose for detection details, or --force to overwrite an existing file. Review the generated configuration before committing it.

.hatch.yml reference

Set version: 1 and declare at least one service. Use short DNS-compatible names such as web and db. Services use those names to reach each other.

Service keyPurpose
build or imageSet exactly one. Use build: . to build the checked-out commit or name an existing image with image.
dockerfileOverride the Dockerfile path for a built service. Use a relative path. Kubernetes resolves it from the build context.
portThe port inside the container. Set it explicitly when routing an app or using an image with a custom port.
exposeSet true on at most one service to route public traffic to it.
envEnvironment variables as strings. Quote values such as "true" and "3000".
depends_onList other service names Hatch should start first.
healthcheckSet cmd and optionally interval_seconds and retries.
limitsSet per-service CPU and memory limits.

For Kubernetes builds, build selects a directory in the GitHub archive. For portability across runtimes, use build: . and an explicit dockerfile path.

Resource limits

Hatch defaults to 1 GiB of memory and 1 CPU per service. Memory accepts k, m and g in powers of 1024. CPU accepts fractional cores up to 16. Namespace quotas can further limit Kubernetes previews.

Health checks

Configure a check for services that need time to become ready. The command runs inside the service with /bin/sh -c and must exit zero when ready. For example, use pg_isready -h 127.0.0.1 -U app -d app for PostgreSQL. depends_on controls startup order. A health check makes that order useful for databases and other dependencies.

SQL seed

Point seed.after at the PostgreSQL service and seed.sql at a repository-relative SQL file. Hatch attempts to run the file after the database becomes ready. It may run again when the preview is recreated, so write it to tolerate repeated execution.

Preview triggers

PR commentAction
@hatchpr previewCreate or update a preview. Put the command alone in the comment.
@hatchpr stopRemove the current preview.

The PR author or a repository collaborator can request a preview. A push or a bare mention will not start one in the default mention mode.

To build automatically when a PR opens, reopens or receives a new commit, add this optional block to your configuration:

previews:
  trigger: auto
  skip_when_only: true
  skip_paths:
    - "**/*.md"
    - "docs/**"

With the GitHub App configured, automatic builds skip a PR when every changed file matches the skip list. An explicit skip_paths list replaces the built-in set of documentation and repository metadata patterns. Set skip_when_only: false to disable the filter. A manual request still works for documentation, tests or other changes.

Variables

Hatch substitutes these placeholders in env values and build paths:

VariableValue
${PR}Pull request number.
${SHA}Full commit SHA.
${REPO}Repository slug.
${DB_PASSWORD}Derived from the repo, PR number and instance webhook secret. Stable across rebuilds of the same PR while that secret stays the same.
${PREVIEW_HOST}Assigned preview hostname.
${PREVIEW_URL}Preview URL, including https://.
${SECRET_NAME}Runtime secret stored as NAME for the repository.

Repository secrets

Add and manage encrypted repository secrets from the dashboard using your instance's admin token. Hatch makes repository secrets available to the preview services at runtime. Use credentials scoped to test systems and only authorize contributors you trust to run that code.

For example, set STRIPE_KEY: ${SECRET_STRIPE_TEST_KEY} under env. The dashboard can export and import encrypted backups. Restore them on an instance with the original encryption key.

BuildKit

Kubernetes uses a remote builder to build from a GitHub archive and push an image to the configured registry. Verify that the Dockerfile can build from an archive without local files or Git history.

The Docker runtime can supply RUN --mount=type=secret values when the operator enables HATCH_BUILDKIT_SESSION and configures HATCH_BUILD_SECRETS. Those settings apply to the Docker runtime. Repository secrets are for runtime use. See the Kubernetes guide for builder compatibility.

Node and PostgreSQL

version: 1
services:
  web:
    build: .
    port: 3000
    expose: true
    env:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
    depends_on: [db]
  db:
    image: postgres:16-alpine
    port: 5432
    env:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: app
    healthcheck:
      cmd: pg_isready -h 127.0.0.1 -U app -d app
seed:
  after: db
  sql: ./seed/preview.sql

Provide seed/preview.sql or omit the seed block. See the Node demo for an application using PostgreSQL.

Python, Redis and PostgreSQL

Use the same db service as in the Node example. Set your web service port, usually 8000 for a Python API, and add a service named redis using redis:7-alpine with port 6379. List both dependencies and set REDIS_URL to redis://redis:6379/0.

Rails and Sidekiq

Run Rails and Sidekiq as separate services. Give the worker a Dockerfile whose default command starts Sidekiq, and keep expose: true on the Rails service only. Set the same database name and Redis URL on both services. Store Rails secrets in the repository secret store. See the Rails and Sidekiq template.

Static site

A root Dockerfile that copies your site into Nginx can use the single-service fallback. If your site needs a build, include that step in the Dockerfile or copy files that are committed to the repository.

FROM nginx:alpine
COPY ./public/ /usr/share/nginx/html/
EXPOSE 80

Isolation and cleanup

Docker Compose uses a dedicated Docker network for each preview. Kubernetes assigns a separate preconfigured namespace with its own resource quota and network policy. Services share the preview's network. Closing the PR removes the preview resources.

Dashboard and logs

Open the dashboard with your instance's admin token to view preview status, build and runtime logs, and repository secrets. You can redeploy or stop a preview from the dashboard.

Preview lifetime

The default expiration time is seven days without a preview update. Operators can change PREVIEW_TTL_HOURS. To recreate an expired preview in manual mode, comment @hatchpr preview again.

Security

  • Set HATCH_ALLOWED_OWNERS to trusted GitHub accounts or organizations. Hatch rejects fork PRs for preview deployment.
  • Use test credentials and keep production secrets out of preview environments. Preview services can read their runtime environment variables.
  • For Docker, see the Docker socket hardening guide. For Kubernetes, use a dedicated builder with mutual TLS and apply the recommended network policies.

Troubleshooting

The bot does not start a preview

Check that the GitHub App is installed for the repository, the owner is allowed, and GitHub delivered issue_comment to the instance. Use the exact command as the entire comment.

The build fails or the service cannot start

Read the build and runtime logs. Check that the Dockerfile builds with all required files in its context. Verify the listening port, service DNS names, and health checks. On Kubernetes, also verify that the builder can reach the registry and preview pods can pull the image.

The preview URL does not open

Check expose: true, the service port, the wildcard DNS and the ingress or tunnel's TLS configuration. A running container alone cannot prove that the public route is reachable.

Current limits

Preview databases are temporary and can be recreated on redeploy. Kubernetes capacity is limited by the configured preview namespaces, their quotas and builder availability.
